## F1：同主题数字路由会误销毁会话

**位置**：`src/host/discourse.ts:30–40`，`src/userscript.tsx:152–158`。

`routeTopicId` 的可选标题段可以吞掉第一段数字，因此 `routeTopicId('/t/123/9')` 返回 `9` 而不是 `123`。与此同时，`topicPermalink` 在没有可用 ASCII 标题段时恰好生成 `/t/123/9`。链接生成与解析不满足往返一致性。

实际产物的离线复现：

1. 主题 `7805` 已载入 6 楼，查询为“脚本安装”。
2. 在同一主题的编码中文标题路径下打开阅读页，“查看首问”生成 `https://linux.do/t/7805/2`。
3. 模拟宿主在同一文档内执行该合法同主题路径的 `history.pushState`。
4. 文档标记仍存在，额外页面导航请求为 **0**；但 ThreadMap 根节点被替换，标题变成“主题 #2 · 已载入 0 楼”，查询变成空字符串。

**影响**：普通同主题导航即可丢失分析和阅读状态；后续加载可能基于错误的主题编号。该复现不是整页重载，也没有安装人工点击拦截器。是否与用户此次事件一致，取决于实站实际路径及导航过程，尚未确认。

**修复建议**：明确区分有标题/无标题路由；链接可统一使用无歧义的同源格式，但仍须修正外部有效路径的解析。加入“生成链接 → 解析主题”的契约，以及中文/编码标题、数字标题、楼层后缀、同主题保持根节点和跨主题清理的回归。不要通过默认持久保存查询或开缓存绕过会话识别错误。

## F2：高分叉接龙存在平方级内存成本

**位置**：`src/core/chain.ts:194,276–285`；默认触发路径为 `src/ui/Widget.tsx:42`；详情还在 `src/ui/ChainView.tsx` 完整渲染兄弟和子楼链接。

每个子楼复制当时的全部 `childrenOf` 到 `siblingIds`，分叉解释又把全部兄弟编号提前拼成字符串。n 个楼接向同一个父楼时，保存的兄弟 ID 总数是 `n(n−1)/2`。单楼合法、回看和回溯有界，均不能限制这一数据结构。

合成样本：一楼“一心一意”，其后各楼“意气风发”，平台回复都指向一楼。预热词典后，每个规模单独运行；每个进程限制 512 MiB 堆、30 秒，最多只测 4,000 个子楼。

| 子楼数 | 建链耗时 | 结果存活、垃圾回收后的新增堆 | 兄弟 ID 条目 | 预先生成的兄弟解释字符 |
| --- | ---: | ---: | ---: | ---: |
| 500 | 9.58 ms | 2,346,872 B | 124,750 | 699,389 |
| 1,000 | 80.64 ms | 7,970,880 B | 499,500 | 2,893,890 |
| 2,000 | 181.20 ms | 30,671,720 B | 1,999,000 | 12,284,390 |
| 4,000 | 463.82 ms | 120,401,120 B（约 114.8 MiB） | 7,998,000 | 52,065,390 |

这不是一次峰值堆测量，而是结果存活时的新增保留堆。20,000 个子楼的公式计数为 199,990,000 个兄弟 ID，**没有冒险执行该规模，也不把公式外推说成实测**。

**影响**：默认自动模式即使面板收起，也会建链识别主题。高分叉输入可能明显卡顿或耗尽标签页内存；常规 2 万楼和“全部无法承接”测试不覆盖这个最坏结构。

**修复建议**：父楼的子列表只存一份，用数量/位置或共享结构表达历史兄弟关系；解释及详情按需、有界展示。保留可追溯依据，不以静默截断原帖替代算法修复。新增同父楼、手动指定父楼和分叉详情的规模回归。

## F3：实时空更新不能可靠清除先前保存的正文

**位置**：`src/host/topic-cache.ts:58–66` 的 `collect`，以及 `src/core/phrases.ts` 的 `mergePost`。

`collect` 先用补全式 `mergePost(before.post, incoming)`；该函数会在新 `raw/text` 为空时保留旧值。此前“新的空正文优先”的检查覆盖的是**从缓存恢复后**的楼层，而非**同一会话先真实观察并写入缓存**的楼层。

复现：开启缓存并保存 `<p>脚本怎么安装？</p>`，随后从 store 提供同 ID 的明确 `cooked: ''`，等待观察和写入窗口后，IndexedDB 中仍是旧正文。对照把同楼改成非空新正文，则能正确更新，排除了“整个更新流程没运行”的解释。

**影响**：缓存可能继续保存和在以后恢复已清空的旧内容，违背当前新观察优先的说明。不是第三方外泄，也没有证明任意缺失正文都等于撤销权限。

**修复建议**：区分字段缺失/占位与明确空正文/删除；不要在缓存的新观测替换上直接复用保留旧正文的合并函数。分别覆盖同会话实时楼、缓存恢复楼、DOM 不完整观测和明确清空。

## F4：空占位被当成当前可读正文

**位置**：`src/host/topic-cache.ts:184–200`，特别是 `readable = posts.length > 0`；`src/core/post-input.ts` 允许缺失/空正文作为合法空观测。

复现：同账号先明确授权保存 6 楼，刷新时页面和 store 仅给出一条 `cooked: ''` 的合法元数据记录。当前 `.cooked` 确实为空，但脚本仍恢复另 5 楼，界面显示已载入 6 楼。

**影响**：没有当前可读正文也能通过缓存恢复门槛。这个门槛本就不能全面认证每楼权限，但当前实现比声明的最低条件还弱。该实验是同账号，不是已证实的跨账号恢复。

**修复建议**：以当前宿主明确提供正文的证据判定可恢复，而不是帖子数组非空；同时不要把纯文本提取器排除了代码/图片后的空文本误当成无正文。无当前正文时保持拒绝恢复，也不主动联网“验证”。

## F5：词组缓存跨主题保留全文，没有字节预算

**位置**：`src/core/phrases.ts:103–122`；`src/host/discourse.ts` 的 `clearPostCache` 只清自己的标准化缓存，未清除此 Map。

`extractPhrases` 以整段帖子文本作强引用键，即使没有识别到词组也保存。条数超过 50,000 才整体清空，不随主题销毁。

有界实验：处理 1,000 条彼此不同、各 19,996 字符的合法纯文本，释放调用方/会话引用并强制垃圾回收后，仍新增保留 **20,234,040 B（约 19.3 MiB）**。这只是 ASCII 样本的本机观测，不是全部字符或浏览器峰值保证。

**影响**：长会话跨主题积累内存；这属于默认内存缓存，关闭可选 IndexedDB 正文缓存不能消除此成本。

**修复建议**：改为随帖子/会话释放的缓存，或同时按字节和条数限制并淘汰；普通非接龙文本不应无限保留为字符串键。保留多次重算收益，但必须覆盖主题切换及长文本负载。

## F6：单楼预算不能限制整份响应和首批工作

**位置**：`src/host/loader.ts:108–117,180–182`，`src/core/post-input.ts:23–25`。

- `response.json()` 一次读取整份响应，没有字节上限；stream 也没有总条数限制。
- 在按本次目标接受楼层前，`batchPosts(initial, ...)` 已遍历并解析全部首批条目。
- 请求计时和中止不能抢占正在执行的同步 JSON/HTML/建链工作，不能代替总量或切片预算。

复现：

1. 使用真正的 `Response`，一份含 12 MiB 无关合法 JSON 字段的响应（总长 **12,583,032 B**）被完整消费，最终只接受 1 楼；本次用时约 129.41 ms。
2. 另用可计数的适配器夹具，目标为 1 楼、首批为 1,000 楼，结果只接受 1 楼，但 1,000 楼均进入正文标准化。字段访问计数仅是探针，不声称 HTTP JSON 可携带访问器。

此前文档已明确单楼上限不是整份响应上限；本项是确认该资源边界仍存在，不将其包装成新发现的跨源漏洞。默认关闭主动加载、5 次请求等策略仍有效。

**修复建议**：确定兼容真实样本的响应字节、stream 和首批条目预算，按实际读取量限制（不能只信可缺失的 Content-Length）；同步批量工作有取消/让出主线程边界。拒绝时保留此前合法进度并明确说明，不自动重试。

## F7：调整宽度的全局监听未随取消/销毁释放

**位置**：`src/ui/Panel.tsx:115–122`。

拖动注册 `window.pointermove` 和 `window.pointerup`，只有 `pointerup` 的 `done` 才清理。探针实际开始拖动，派发 `pointercancel` 后离开主题；面板根节点已移除，两条监听仍存在。

**影响**：可能保留旧面板/宿主引用并继续响应之后的指针事件。这里只测了监听存活，没有将其量化为具体泄漏字节。

**修复建议**：把拖动的取消函数纳入组件卸载，处理 pointercancel / 失去捕获等终止路径，避免旧拖动在新主题提交偏好。与 `useDockDrag` 已有的取消处理保持职责一致。

## N1：用户实站原标签刷新，根因仍未定

**相关位置**：`src/ui/PostLink.tsx:19–25`，`src/host/navigation.ts`。

实际产物在无其他脚本干预的离线浏览器中：

- 首问在 DOM 中：页内定位，原页状态保留。
- 首问不在 DOM 中：新标签打开，原页 6 楼、查询和阅读上下文保留。

另外构造了一个**明确标注为人工模拟**的宿主点击捕获器：它在捕获阶段忽略 `target=_blank` 并在原页导航。实际产物中的 `stopPropagation()` 到目标/冒泡处理时已经太迟，原文档仍被重载。该实验解释了一个现有保护无法覆盖的失败边界，**不证明真实 Discourse 或 Tampermonkey 正在这样做**。

F1 则是无需该拦截器即可复现的独立会话错误。真实事件应先区分整页导航与同文档会话重建，再核对前后路径、导航请求发起者和点击事件顺序。不要用广泛阻断论坛事件、关闭浏览器保护、自动开缓存或自动重抓正文作为未经验证的修复。

实站验收必须覆盖：定位首问 → 查看原帖 → 继续面板阅读，已载入数量、查询、列表页码与阅读位置不丢失；缓存关闭也应成立。

## V1：配色统一反馈

**位置**：`src/ui/tokens.ts:35–57`，`src/ui/styles.ts:64–69`，`src/host/theme.ts`。

当前固定浅色强调色为 `#0063a6`，深色为 `#75c8ff`；普通提示仍偏灰绿，焦点/定位反馈为棕黄。宿主适配只判断深浅模式，不读取论坛强调色。蓝色承担操作/选中语义，能与成功、警告、错误区分，固定值也便于测试对比度；但这不证明固定蓝色是最佳选择，更不等于与论坛主题一致。

建议收敛为：中性表面、普通按钮和普通提示；主要操作/链接/选中态共用单一强调色，优先与宿主一致且验证实际对比度；绿/黄/红只用于真正的状态提示，减少大色块。无法安全采用宿主色时采用明确的中性方案，而非偷偷引入另一套品牌色。

本轮没有边审计边修改颜色。后续改色仍需同时检查实际普通/悬停/选中/焦点状态、深浅背景和字号，不能只令十六进制颜色一致，也不能放宽既有对比度断言。
