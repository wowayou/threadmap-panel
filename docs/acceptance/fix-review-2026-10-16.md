## 发现（按本项目修复优先级）

### R1 / P1：全部当前可读正文被明确清空时，旧缓存未清除，刷新后可再次恢复

- 位置：`src/host/topic-cache.ts:68–86,184–201`。
- 原因：`observe` 先将 `readable` 设为 false；虽然 `collect` 能收集明确空正文，`schedule` 和 `flush` 都因 `!readable` 提前返回。禁止恢复/新增保存的门槛同时挡住了清除旧正文的写入。
- 实际产物 + 真实 IndexedDB：先保存 2 楼，将两楼的 `cooked` 都明确改为 `''`，触发观察并等待 1.6 秒，数据库仍保留两份旧正文。随后刷新，仅让第 2 楼提供真实正文，**被清空的第 1 楼作为缓存重新出现**。
- 同页对照：只清空第 1 楼、第 2 楼仍可读时，空正文确实落盘；恢复非空正文也能落盘，排除了观察/写入流程没运行的解释。上轮测试始终保留至少一楼可读正文，未覆盖从“可读”到“全部不可读”的转换。
- 修复方向：把有权限约束的恢复/新增保存与撤销旧内容分开。明确清空不能依赖另一个楼仍然可读；卸载与在途写入也需同样覆盖。不要通过放开历史恢复门槛解决。

### R2 / P2：占位变成真实正文后，`bodyMissing` 标记残留，启用缓存仍存不进去

- 位置：`src/core/phrases.ts:166–175`。
- 原因：`{ ...existing, ...incoming }` 会保留旧的 `bodyMissing: true`；真实新正文没有这个可选字段，不会自动删除它。代码只处理了“真实 → 缺失”，未处理“缺失 → 真实”。
- 纯函数探针：先解析缺失 `cooked` 的记录，再合并真实正文；输出同时有 `text: '当前正文'` 与 `bodyMissing: true`。
- 实际产物：缓存关闭时先出现占位，再出现真实正文，之后用户启用缓存；开关为 true，但提示“当前没有可缓存的合法楼层”，数据库主题数为 0。对照刷新后从真实正文开始，同一许可下能保存 1 楼。
- 修复方向：正文观测状态必须随新正文更新；覆盖初次占位、编辑、清空、缺失四种转换，核验会话与落盘两条链路。

### R3 / P2：缺失正文但元数据改变时，会重写旧正文并刷新其保留时间

- 位置：`src/host/topic-cache.ts:58–65`，`src/core/phrases.ts:168–180`。
- 原因：`collect` 先用 `mergePost` 补回旧正文并去掉缺失标记，再以 `Date.now()` 生成缓存。点赞等元数据一变，记录就被当成新的正文观测。
- 实际产物 + 真实 IndexedDB：已经保存的第 2 楼更新为缺失 `cooked`、`like_count: 9`（第 1 楼保持可读）。数据库仍保存旧正文，且 `seenAt` 从 `1792156498828` 增为 `1792156498997`（最终复跑记录）。
- 这证明“没有新正文观测却续期”，未冒充等待 24 小时后的实测；它与文档“缺失观测不写缓存、不刷新旧记录”的承诺不符。
- 修复方向：正文的新鲜度与元数据更新不能混为一谈；不得以补全后的记录推断刚刚重新看到了正文。

### R4 / P2：只含空 HTML 标签的占位仍能触发缓存恢复

- 位置：`src/core/post-input.ts:61`，`src/host/topic-cache.ts:187–188`。
- 原因：`hasBody` 只检查 `raw.trim() !== ''`，能拒绝空字符串和空白，不能区分真正内容与 `<p></p>`。
- 实际产物：先授权保存 2 楼；刷新时页面/store 只提供第 1 楼 `cooked: '<p></p>'`，DOM 正文可见文本为空，仍恢复第 2 楼缓存；同一场景将输入换成 `''` 时不恢复，确认漏洞在空 HTML 结构而非空串门槛失效。
- 修复方向：检查真正的内容证据，空结构/注释不算；图片与代码等有内容但被分析文本提取器排除的正文仍须允许。不能改成简单检查提取后文本非空。
- 仍只是同账号的恢复门槛不足，不是已证实的跨账号访问。

### R5 / P2：首批按目标裁剪后，能漏掉已接受 ID 的后续冲突

- 位置：`src/host/loader.ts:74–84,231`。
- 原因：`selectInitial` 按条目数截断新增项，再交给 `batchPosts` 检查。排在目标之外的同 ID 冲突没有参与验证。
- 真正的 `Response` 合成响应：stream 为 `[1]`；首批同时返回 `{ id: 1, post_number: 1 }` 与 `{ id: 1, post_number: 2 }`。目标 1 楼时成功接受第一条；仅把目标改为 2 楼，同一响应被判异常。输入可信度不应依赖用户选择的新增目标。
- 修复方向：可避免解析不用的正文，但已选择 ID 的身份冲突不能因裁剪消失；加入“跨目标边界的重复/冲突/坏记录”回归。

### R6 / P2：50 万 stream 上限只覆盖主题 JSON，没有覆盖默认页面数据路径

- 位置：`src/host/loader.ts:203–209`，`src/host/discourse.ts:79`，`src/core/post-input.ts:24–25`。
- 原因：上限只在读取 `/t/{id}.json` 后检查；页面 `readStore` 和已知 `options.stream` 都直接调用不带总数限制的 `parseStream`。
- 有界探针（512 MiB 堆、40 秒进程限制）：500,001 个合法 ID 被 `readStore` 接受；同一列表交给 loader，目标 1 楼，仍发出 1 次请求并成功返回 500,001 项 stream。
- 修复方向：明确所有入口共同的容器预算与拒绝语义；不能在文档中把仅网络主题 JSON 的检查写成所有 stream 的保证。
- 16 MiB 网络响应实际字节上限本身的既有测试通过；此项不否定该限制。同步 JSON 解析未切片也是上轮已承认的限制，不重复计为新发现。
